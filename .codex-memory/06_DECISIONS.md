# Decisions

## 2026-05-08 Centralized Settings

Контекст: настройки не должны задаваться вручную на каждом телефоне сотрудника.

Решение: настройки хранятся централизованно в Google Sheets / Apps Script и подтягиваются формой при старте, при возврате вкладки в фокус и раз в 6 часов.

Альтернативы: localStorage на каждом устройстве; хардкод в `index.html`; отдельная база данных.

Последствия: руководитель меняет настройки один раз, все сотрудники получают обновления; нужно аккуратно разделять публичные настройки и секреты.

## 2026-05-08 Telegram Secrets Server-Side

Контекст: репозиторий публичный, Telegram Bot Token нельзя держать в браузере.

Решение: секреты Telegram должны жить в Apps Script `PropertiesService`; Apps Script отправляет сообщения и фото.

Альтернативы: отправка напрямую из `index.html`; хранение токена в localStorage; хранение токена в GitHub repo.

Последствия: безопаснее для публичной формы; нужно убрать оставшийся legacy client-side Telegram code.

## 2026-05-08 GitHub Pages And Custom Domain

Контекст: форма должна открываться простой ссылкой с телефона.

Решение: публиковать `main` через GitHub Pages, использовать кастомный домен `no-money-no-honey.ru`.

Альтернативы: Netlify; Apps Script HTML as frontend; локальный HTML.

Последствия: простой deploy через GitHub; повышенные требования к секретам из-за публичности repo.

## 2026-05-08 Native Calendar

Контекст: календарь не срабатывал стабильно; пользователь спрашивал, можно ли менять дизайн календаря.

Решение: использовать системный `input[type=date]`, не писать кастомный календарь.

Альтернативы: кастомный календарь на JS; UI-library.

Последствия: меньше кода и выше мобильная надёжность; дизайн календаря контролируется устройством, а не приложением.

## 2026-05-08 Remove +/- 3 Day Limit

Контекст: руководителю нужно внести данные начиная с 1 мая, но сотрудники не должны свободно менять давние смены.

Решение: снять ограничение `±3 дня`, но блокировать даты старше 2 дней для обычного сотрудника.

Альтернативы: оставить `±3 дня`; разрешить всем любые даты; внедрить полноценные роли и аудит.

Последствия: проще внести историю, но старые даты защищены от обычного сотрудника.

## 2026-05-08 Owner Retro Entry

Контекст: ретроввод должен быть доступен руководителю, но в отчёте должен стоять реальный сотрудник смены.

Решение: при старой дате показывать fullscreen blocker, после PIN руководителя открыть выбор сотрудника.

Альтернативы: ручной ввод в таблицу; отдельный админский сайт; роли и логирование.

Последствия: исторические смены лучше вносить через форму; логирование действий руководителя пока не нужно.

## 2026-05-08 Project Memory

Контекст: пользователь хочет открывать новый диалог Codex и продолжать без потери контекста.

Решение: создать `.codex-memory/` с numbered markdown files.

Альтернативы: держать контекст только в чате; расширять только README.

Последствия: новый Codex должен читать файлы по номерам; папка не добавляется в `.gitignore`, пока пользователь не скажет, что память локальная.

## 2026-05-08 Canonical Workspace Path

Контекст: в сессии обнаружилось несоответствие рабочей папки (`Etna WEB` vs `RestForm`), из-за чего можно править не тот проект.

Решение: считать канонической рабочей папкой только `/Users/rio/Desktop/RestForm` и выполнять все изменения именно там.

Альтернативы: поддерживать две копии и синхронизировать вручную.

Последствия: меньше риска правок не в том репозитории; перед каждой сессией проверять `pwd`.

## 2026-05-08 Commit Memory To Repository

Контекст: пользователь подтвердил, что `.codex-memory/` нужно хранить в репозитории и коммитить.

Решение: `.codex-memory/` остаётся версионируемой частью проекта и не добавляется в `.gitignore`.

Альтернативы: локальная память вне Git; хранение только в чате.

Последствия: новый диалог Codex можно поднимать сразу по файлам памяти; при изменениях логики нужно синхронно обновлять memory-файлы.

## 2026-05-08 Dynamic Apps Script Deployment URL

Контекст: при каждом новом deployment Apps Script Web App URL может меняться, а обновления backend делаются часто.

Решение: хранить в памяти текущий URL как оперативный, но считать его изменяемым; после backend-правок обязательно проверять живой endpoint и обновлять `window.APPS_SCRIPT_URL`, если deployment URL изменился.

Альтернативы: считать URL постоянным; обновлять frontend без проверки endpoint.

Последствия: handoff должен явно фиксировать актуальный URL на момент сессии; исключается ложная уверенность в постоянстве endpoint.

## 2026-05-08 Telegram Identity Deferred

Контекст: имя/username Telegram-бота сейчас не критичны для разработки формы и будут уточнены ближе к релизу.

Решение: в документации оставить плейсхолдер `<TODO: уточнить у пользователя>` до отдельного подтверждения.

Альтернативы: заполнять догадками; принудительно требовать данные сейчас.

Последствия: техдолг минимальный, но перед релизом обязательна финальная проверка Telegram-метаданных.

## 2026-05-09 Direct Google Sheets Integration

Контекст: пользователь ожидает, что Codex будет править не только форму и Apps Script, но и саму Google-таблицу.

Решение: использовать Google Drive/Sheets integration для чтения и правки живого spreadsheet, особенно при изменениях колонок, строк, форматов и формул.

Альтернативы: давать инструкции пользователю; менять только код и ждать ручных правок таблицы.

Последствия: Codex должен сверять live sheet перед структурными изменениями и не считать задачу завершённой, если код обновлён, а таблица нет.

## 2026-05-09 Apps Script Deployment Via Clasp

Контекст: ручной деплой Apps Script замедлял работу и создавал зависимость от пользователя.

Решение: настроить `clasp` с OAuth и деплоить Apps Script из проекта Codex.

Альтернативы: продолжать ручные deployments; использовать только Apps Script UI.

Последствия: backend можно обновлять быстрее; нужно сохранять `.clasp.json`, `.claspignore`, `appsscript.json` и не забывать version/deploy после push.

## 2026-05-09 Keep Code.gs And Код.js Synced

Контекст: bound Apps Script project содержит файлы `Code.gs` и `Код.js`. Если они расходятся, старые функции могут shadow/конфликтовать с новыми.

Решение: держать оба файла синхронизированными и пушить оба через `.claspignore`.

Альтернативы: удалить `Код.js` из Apps Script project; поддерживать только один файл.

Последствия: меньше риска старого `doGet`/`doPost`; есть временное дублирование файла в репозитории, пока проект не будет безопасно очищен.

## 2026-05-09 Yandex Food As Card Revenue

Контекст: сначала обсуждалось, что `Яндекс еда` будет только переноситься в таблицу и не входить в дневную выручку; затем пользователь уточнил, что она должна учитываться как безнал.

Решение: добавить `Яндекс еда` как отдельный доход в форме и таблице, считать его частью `Безнал итого` и `Выручка итого`.

Альтернативы: не учитывать в выручке до будущей настройки комиссий; учитывать отдельной аналитической строкой.

Последствия: текущие дневные показатели включают `Яндекс еда`; будущие комиссии и удержания нужно добавлять отдельной настройкой, не ломая текущую схему.

## 2026-05-09 Sheet Style Is Product UI

Контекст: пользователь указал, что новая колонка была визуально не в стиле таблицы и заголовок не был выровнен.

Решение: считать оформление Google Sheets частью продукта. Новые колонки должны копировать стиль соседних колонок бизнес-блока без запроса цветов у пользователя.

Альтернативы: просить пользователя давать точные цвета; оставлять таблицу функциональной, но визуально сырой.

Последствия: при каждой правке листа нужно проверять форматирование, выравнивание, merged-секции, ширины, числовые форматы и alternating backgrounds.

## 2026-05-09 Live Sheet Is Source Of Truth

Контекст: пользователь спросил, может ли вручную редактировать таблицу, и будет ли Codex это учитывать.

Решение: пользователь может вручную редактировать Google Sheets. Перед изменениями структуры, формул или оформления Codex обязан читать live sheet и учитывать фактическое состояние.

Альтернативы: запретить ручные правки; поддерживать только кодовую миграцию.

Последствия: меньше ограничений для пользователя; больше ответственности на Codex перед каждой табличной правкой.

## 2026-05-09 Prefilled Date Rows

Контекст: если форма пишет в первую свободную строку, пропущенные дни могут нарушить порядок и затруднить ретроввод.

Решение: заполнить `Данные` датами с 2026-05-01 по 2026-08-31 и использовать поиск строки по выбранной дате как основной сценарий записи.

Альтернативы: продолжать писать в первую пустую строку; создавать строки динамически только при отправке.

Последствия: пропущенные дни остаются пустыми, а поздние отправки попадают в свою дату; при расширении периода нужно заранее добавить новые даты или сделать безопасное автопродление.
